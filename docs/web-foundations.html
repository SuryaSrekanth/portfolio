01 The three languages of the web

Everything else in this document exists to help you write these three things more comfortably.

The same page, three times. Each language adds one layer.

A browser understands these three and nothing else. That is the single most important fact in this document. Every tool below eventually produces HTML, CSS, and JavaScript, because that is the only thing a browser can run.

In a line HTML is the structure, CSS is the look, JavaScript is the behaviour. Browsers speak only these three.

03 Node.js

JavaScript, but running on your computer instead of inside a browser.

JavaScript was invented to run inside web browsers, and for about twenty years that was the only place it could run. Node.js took the JavaScript engine out of the browser and made it a program you can run on your own machine, like Python or Java.

Before Node
  • Browser → runs JavaScript ✓
  • Your terminal → cannot ✗

Build tools had to be written in other languages.

After Node
  • Browser → runs JavaScript ✓
  • Your terminal → runs it too ✓

Now the tools can be JavaScript as well.

Node is the engine your build tools run on. Visitors never install it.

node -v
v20.20.2
In our project

Node 20 is installed. We hit a real consequence: the package manager pnpm refused to run because it requires Node 22. We used npm instead and lost nothing. Version numbers are not decoration.

In a line Node lets JavaScript run on my computer, not just in a browser, so build tools can be written in it.

04 npm

A way to download and manage code other people have written.

npm stands for Node Package Manager, and it is two things at once: a public library of over two million free code packages, and the command-line tool that fetches them. A package is simply a folder of reusable code that solves one problem, so nobody has to solve it twice.

Why node_modules gets so big

You asked for four packages. You received 362. Here is why: 

portfolio/
├── next            you asked for this
│   ├── postcss        next needs it
│   ├── styled-jsx     next needs it
│   └── …              and those need more again
├── react           you asked for this
├── tailwindcss     you asked for this
└── typescript      you asked for this

= 362 packages actually installed

Packages depend on packages. This is the real count from our install.

You never edit node_modules, never read it, and never commit it. It is a build artifact: generated from instructions rather than written by hand. Delete it and npm install recreates it exactly.

npm versus npx

npx runs a package once without installing it permanently. That is why we wrote npx create-next-app: we needed that tool for a single moment to generate the project, and never again.

In a line npm downloads code other people wrote and remembers which versions my project uses.

05 package.json

The one file that describes your whole project to the tooling. Here is the real one, annotated.

"scripts": {
  "dev":   "next dev",
  "build": "next build"
}

Shortcuts you type npm run dev really runs next dev. You are not memorising commands, you are reading them off this file.

"dependencies": {
  "next":  "16.2.12",
  "react": "19.2.4"
}

Needed by the finished site These ship. They are part of what makes the live website work.

"devDependencies": {
  "tailwindcss": "^4",
  "typescript":  "^5"
}

Needed only while building Exactly the left-hand column of the diagram in section 2. These never reach the visitor.

Three sections, three jobs. The split mirrors where code runs.

What the caret means

"^4" means "version 4 point anything, but not version 5". The caret allows safe updates while blocking versions likely to break things. "16.2.12" with no caret means exactly that version and nothing else.

In a line package.json lists what my project needs and defines the shortcut commands I type.

06 React

A way to build a page out of reusable pieces instead of one long file.

Plain HTML
<article> card 1 …</article> <article> card 2 …</article> <article> card 3 …</article> <article> card 4 …</article> <article> card 5 …</article> <article> card 6 …</article>

Add a button, edit six places, hope you missed none.

With React 
function Card({ project }) {
  return <article>
    {project.title}
  </article>;
}

projects.map(p =>
  <Card project={p} />
)

Add a button once. All six update.

Describe the piece once, then repeat it over your data.

Those HTML-looking tags inside JavaScript are JSX. It is not really HTML, it is JavaScript that gets converted into instructions for building HTML. It just reads better than the alternative.

In our project

This is exactly why deleting four placeholder projects from site.ts made four cards disappear with no other change. Change the list, the page follows.

In a line React lets me describe a piece of the page once and reuse it, so changing it means editing one place.

07 Next.js

React on its own is unopinionated. Next.js supplies the missing structure.

React only handles building interfaces from components. It says nothing about pages, URLs, images, fonts, or how to turn your work into files a web server can serve. Next.js is a framework: React plus answers to all of that.

Where a file lands is the configuration

  • src/app/page.tsx the home page, /
  • src/app/icon.svg the favicon tag
  • src/app/opengraph-image.png the social share card
  • public/resume.pdf /resume.pdf

No configuration written by hand. The filename is the instruction.

Beyond routing, here is what it did for us concretely:

FeatureWhat it did
Image optimisationScreenshots are 1200x750, but cards received a 576x360 version, generated to suit the screen.
Font handlingThree fonts downloaded at build time and served from our own domain, so text never jumps while loading.
PrerenderingFinished HTML generated once at build time, so visiting requires no server work.
Version matters

Next.js 16 changed behaviour most tutorials still assume. One real example: it no longer smooths scrolling during navigation unless you add data-scroll-behavior="smooth". We found this in the docs bundled inside node_modules, not in older guides.

In a line React builds the pieces; Next.js decides how pages, images, fonts and files all fit together.

08 TypeScript

JavaScript that checks your work before you run it.

In plain JavaScript, a typo is only discovered when the code runs, and sometimes not even then. TypeScript lets you describe the shape of your data, then warns you the moment something does not match. 

type Project = {
  title: string;
  kind: "web" | "mobile" | "ai";   // only these three
  liveUrl?: string;                // ? means optional
};
✓ ACCEPTED 
{ title: "Yarn AI",
  kind: "web" }
✗ REJECTED 
{ title: "Yarn AI",
  kind: "webb" }

Type '"webb"' is not assignable to type '"web" | "mobile" | "ai"'.

The error appears in your editor as you type, long before the browser.

The ? is quietly powerful. It says liveUrl may be missing, which forces you to handle that case. That is exactly why project cards without a live link fall back gracefully instead of rendering a broken button.

In a line TypeScript is JavaScript where I describe what my data looks like, so mistakes get caught while typing.

09 Tailwind CSS

Styling by composing small named classes, instead of maintaining separate stylesheets.

Traditional CSS · two files 
/* styles.css */
.project-card {
  display: flex;
  padding: 24px;
  border-radius: 16px;
}
<!-- index.html -->
<div class="project-card">

Invent a name, then keep two files in sync forever.

Tailwind · one line 
<div class="flex p-6 rounded-2xl">

No naming, no second file, no hunting.

Each class does one small thing. What you read is what you get.

Design tokens keep it consistent

Tailwind's real strength is defining your palette once, then using it by name everywhere: 

@theme inline {
  --color-ink:    #141221;
  --color-violet: #9333ea;
}

That block is what makes text-ink and bg-violet valid classes. Change the hex once and the entire site follows. No hex code is ever typed into a component.

In our project

This is what made the dark-mode accessibility fix a one-line change. We added a token called --on-accent that flips colour with the theme, and every button using it was corrected at once.

In a line Tailwind styles things with small classes on the element, using a palette I define once.

10 The dev server and the build

Two ways of running the same project, for two different purposes.

  • You write Source files TypeScript, JSX and Tailwind classes
  • npm run build The build Types checked then removed, CSS collected, code compressed
  • Visitors get Plain files HTML, CSS and JavaScript, nothing else

The build is the boundary from section 2, doing its work.

npm run devnpm run build
PurposeFast feedback while workingThe real website
Wherelocalhost:3000, your machine onlyFiles you upload
OptimisedNo, that would slow it downYes, fully
On saveBrowser updates instantlyYou run it again
The most important lesson we learned

A successful build does not mean the page is correct.

Every one of the five bugs we found passed the build cleanly. Dark mode failed accessibility contrast, and the page scrolled sideways on mobile, while the terminal reported success. The build checks that your code is valid. Only opening the page checks that it is right.

In a line Dev mode is for fast feedback; build makes the real site. Neither proves the page looks correct.

11 How it all fits together

The same six tools, stacked in the order they depend on each other.

Your site The portfolio a visitor actually loads
Tailwind Applies the design system consistently
Next.js Pages, images, fonts, and the build itself
React Builds the page from reusable components
TypeScript Catches mistakes as you type
npm Downloads all of the above and tracks versions
Node.js The foundation. Lets every tool above it run at all

Read it bottom to top. Each layer needs the ones beneath it.

The honest one-paragraph version: Node lets the tooling run. npm fetched Next.js, React, TypeScript and Tailwind into node_modules. You write components in React using JSX, with TypeScript checking your data and Tailwind classes handling appearance. Next.js takes all of it, runs the build, and produces plain HTML, CSS and JavaScript. That output is the only thing a visitor ever downloads.

Worth remembering

None of these tools are required to make a website. You can build a perfectly good one with three files and no tooling at all. They exist because they make larger sites easier to change safely, which matters the moment a project outgrows a single page.

12 Command reference

Everything you actually need to type, and what each one does.

CommandWhat happens
npm installDownloads everything listed in package.json
npm run devStarts the local site at localhost:3000
npm run buildBuilds the real, optimised website
npx tsc --noEmitChecks types without creating files
npx eslint .Checks code quality and common mistakes
node -vPrints your Node version

The habit worth building: run all three checks, then open the page and look at it. The terminal tells you the code is valid. Your eyes tell you it is right.
